# Практический перенос эмуляции на другую модель камеры

Дата: 2026-11-12. Это инструкция исследования и воспроизведения на компьютере,
не инструкция установки прошивки. Она не обещает поддержку любой камеры.
Переносим метод проверки и отдельные программные компоненты; совместимость
каждой модели и каждой версии прошивки доказываем заново.

## 1. Что именно опубликовано

В этом проекте две связанные, но самостоятельные системы:

1. **OM-Emu**: независимый JavaScript-эмулятор MN10300/AM33 с моделями устройств,
   настоящим исполнением частей ядра uITRON, GUI и приложения камеры. Непокрытые
   устройства и службы заменены явно названными моделями. Исходники OM-Emu
   находятся у автора, а не скопированы в этот репозиторий.
2. **E-PL9 Lab**: собственные ограниченный MN103-интерпретатор и проверки
   участков firmware, логическое хранилище компонентов, адаптер штатного
   updater, пассивное наблюдение за OM-Emu и строгая проверка его результатов.
   Это не второй независимый полнофункциональный эмулятор камеры.

Новая связка имеет следующий путь данных:

```
точный приватный update-пакет
  -> штатные инструкции updater E-PL9 в ограниченной CPU-модели
  -> моделируемые листья program/readback
  -> сохранённые main.flash.bin и osd.flash.bin
  -> закрытие и повторное открытие файлов без перезаписи RAM-копии
  -> независимые полные проверки оболочек, содержимого и происхождения
  -> payload именно этих сохранённых файлов
  -> отдельные свежие сеансы OM-Emu
  -> GUI-состояния, диагностика, PNG/RGB и проверки возврата к stock
```

Реальный физический reset/boot между этими этапами не исполняется. У E133 в
закреплённом OM-Emu нет входа `res_nand`; `loadNand()` возвращает `null`.
UI получает проверенные main/resource через обычный загрузчик лаборатории.
Логические `*.flash.bin` нельзя выдавать за полный дамп NAND.

Собственные новые точки входа:

- [epl9_virtual_flash.py](../scripts/epl9_virtual_flash.py): сохраняемое
  логическое хранилище main/OSD и инъекции отказов.
- [epl9_virtual_install.py](../scripts/epl9_virtual_install.py): исполнение
  проверенных инструкций updater и квитанции записей/чтения.
- [epl9_virtual_flash_ui.py](../scripts/epl9_virtual_flash_ui.py): проверка
  квитанций и данных, четыре сеанса UI и сравнение.
- [Описание updater](epl9-virtual-installation.md),
  [описание UI-моста](epl9-virtual-flash-ui.md),
  [исходный native-source-v1 пакет](epl9-native-source-v1-package.md).

Нынешние `epl9_*` CLI **специально привязаны к E-PL9 build 1101 и точным хэшам**.
В них нет универсального `--model`. Замена имени модели или хэша не является
портированием и не должна превращать отказ проверки в успешный результат.

Для собственной цепочки updater/store/UI здесь квалифицирован только Linux.
Хранилище использует `os.O_NOFOLLOW`, а потребитель закрепляет Linux MN103 reader
с точным именем и SHA-256. Windows/macOS требуют отдельного адаптера и
квалификации, не переименования executable. Возможности upstream player на
другой ОС не означают поддержку наших CLI на ней.

## 2. Что уже проверено, а что нет

Для E-PL9/IM008, код E133, model bytes 1330, build 1101:

- В сохранённом прогоне updater `run-v4` проверены 13 полноразмерных сценариев:
  кандидат, возврат stock, повреждённые входы, ошибки записи/чтения и явно
  моделируемые прерывания. Обе успешные пары компонентов после повторного
  открытия совпали с целевыми полными байтами.
- Четыре свежих сеанса UI дали по 41 кадру: stock, только значки, кандидат,
  возвращённый stock. Все 41 кадр возвращённого stock совпали с исходными
  пикселями, состояниями управления и диагностической историей. Кандидат
  совпал с контролем «только значки»; отличия от stock ограничены значками.
- Текущая строгая UI-квалификация имеет SHA-256
  `c5ab7fc1d4e8da446d2861edb3ad8ce2f36cf465507ce3a9e4a87c5f70460ddd`.
  Это идентификатор сохранённого отчёта, а не замена его приватных входов.
- Все шесть счётчиков участков обработки в этом UI-маршруте остались нулевыми.
  **Фотографические пиксели Gold/Portra, TruePic/ISP и завершение настоящего
  задания обработки этим маршрутом не проверены.**

Счётчики и снимки меню не доказывают работу сенсора, SD-контроллера, Delete,
31 рецепта, физической записи flash или восстановления после неудачной
загрузки. Известная stock-диагностика BMP_LUT сохранена и сравнена, а не скрыта.
`install_ready=false` остаётся в силе.

Эта публикация не меняет принятый ART-only BIN. Будущие 31 рецепт, SD-слоты и
переключение Delete должны иметь отдельные версии, выходы и доказательства.

- публичные собственные исходники, тесты, документацию и хэши;
- независимые upstream checkouts в игнорируемом `references/`;
- законно полученную прошивку, decoded-компоненты, пакеты, overlays и сырые

GitHub-клон проекта сам по себе не содержит необходимые firmware-входы.
Получите точный файл из разрешённой приватной копии либо официального канала
производителя. Запишите модель, отображаемую версию, внутреннюю сборку, размер,
SHA-256, источник и разрешённый способ использования. Одинаковая надпись «1.1»
не доказывает совпадение байтов. Обновление производителя не является полным
readback конкретного корпуса и обычно не содержит всех его калибровок/BOOT.

## 4. Сначала проверьте существующий порт

У OM-Emu есть реестр моделей и версии их прошивок. Его исходная модель E143
не является универсальной адресной картой. В закреплённом README есть E133,
но наличие записи модели и успех её menu smoke не означают полный аппаратный
эмулятор. Другие производители и CPU-архитектуры могут требовать совершенно
нового backend.

Для уже поддержанной upstream модели начните с **немодифицированной** версии.
Пример ниже использует E133; выберите код только из реального списка:

```sh
git clone https://github.com/flatpanda/om-emu.git references/om-emu
git -C references/om-emu checkout --detach 147ca89c60b24774f3145c2813d79714e0f0b7b7
cd references/om-emu
node --version
node emu/bin/fetch-fw.mjs --model list
node emu/bin/fetch-fw.mjs --model E133 --bin /absolute/path/to/exact-authorized-stock.BIN
node emu/bin/fetch-fw.mjs --model E133 --check
node emu/bin/test-pure.mjs
node emu/bin/modelcheck.mjs E133 --no-port
node emu/bin/play.mjs --model E133 --no-browser
```

Это команды интерфейсов закреплённых исходников, а не сообщение о новом
выполнении здесь для всех моделей. Нужен Node 26 или новее по upstream;
сохранённая E-PL9 квалификация использовала официальный Linux Node v26.13.0
с SHA-256 executable
`0adde40d1b7dfa57c8bc83cbc319758c3ec6ebba21363bb2fa752ea6b267ad1b`.
Новая ОС/Node или новая upstream ревизия требуют отдельного отчёта.

`fetch-fw` может обратиться к официальному updater API, если подходящего
локального файла нет. Если API выдаёт более новую версию, чем закреплённая,
проверка откажет. Не отключайте хэш-контроль; заведите отдельный порт новой
сборки. Не используйте сетевой отказ как повод брать неизвестные firmware.
`modelcheck --no-port` проверяет существующие таблицы, не генерируя их заново.
Он пропускает модели без распакованной firmware и может завершиться с exit 0
без их исполнения. Требуйте успешный `fetch-fw --check` и фактическую строку
результата E133/TFT в выводе `modelcheck`; если её нет, отметьте not-run, а не
успех. Для другой модели и EVF требуются их собственные строки результата.
Даже S2/playback используют объявленные модели устройств; это не проверка
настоящего изображения сенсора.

Для E-PL9-моста нужен настоящий локальный checkout `references/om-emu`, а не
симлинк на корень другого checkout: пассивный observer привязывает загруженные
ESM-модули к точному URL-префиксу. Отдельные разрешённые read-only firmware
fixtures могут быть ссылками, если соответствующий потребитель это разрешает.
Строгие manifests компонентов UI-моста симлинки не принимают.

## 5. Если модели или точной сборки нет: порядок исследования

### Шаг A. Установите платформу, не предполагая её по названию камеры

1. По документации производителя и разрешённому образу определите код модели,
   контейнер, секции, тип CPU/ISA, endianness и адресные пространства.
2. Сверьте признаки ISA с декодированием нескольких независимых функций,
   условных переходов, вызовов и таблиц. Для MN103 проверьте AM33-вариант и
   правила адресации/кэша; для ARM и других ISA этот MN103 backend не подходит.
3. Найдите runtime base, startup copy/expand таблицы и RAM/MMIO-карту. Адрес
   в encoded update, decoded секции, flash alias и runtime RAM различается.
   E-PL9 адреса `604...`, `806...` или `988...` нельзя переносить численно.
4. Запишите источник каждого вывода: документация, статический код, ограниченное
   исполнение, модель или реальное измерение. Не заполняйте неизвестное нулями.

Результат: отдельный паспорт точной сборки с хэшами и картой неизвестного.
При неподдерживаемой ISA, недоступном законном образе или неизвестном способе
декодирования перенос на этом уровне остаётся заблокированным.

### Шаг B. Разделите общий движок и адаптацию платы/сборки

У upstream за это отвечают следующие реальные файлы:

- `emu/src/core/`: CPU, память и интерпретатор;
- `emu/src/fw/models.mjs`: точные firmware, размеры, runtime base и панели;
- `emu/src/fw/board.mjs`: семейства платы, MMIO, IRQ, таймеры, VSC/OSD, SCPU;
- `emu/src/fw/xmap.mjs`, `place.mjs`, `facts.mjs`: сопоставление функций/данных
  и получение фактов из целевого образа;
- `emu/bin/port.mjs` и `emu/src/fw/ports.mjs`: генератор и результаты адресного
  перевода, факты и перенесённые knobs;
- `emu/src/fw/model.mjs`: `A()`, `fact()`, `knob()`, UNMAPPED и
  `refuseUnmapped()`; `emu/src/lab/`: harness, службы и явно названные stand-ins.

Сначала ищите близкую **по коду и плате**, а не по маркетинговому поколению,
поддержанную сборку. Для сопоставления проверяйте вызовы, литералы, таблицы
задач/очередей, ресурсные загрузчики и инварианты структур. Один совпавший
текстовый литерал или похожая сигнатура недостаточны. Ручной override должен
иметь адрес исходной и целевой сборки, точные проверенные байты и объяснение.

В отдельной разрешённой рабочей копии после добавления всех нужных данных
модели upstream-команда `node emu/bin/port.mjs TARGET_CODE` пересчитывает порт.
Она требует также точную firmware исходной E143 и, при цепном переносе,
референсных сборок. Генерируемый `emu/out/port/TARGET_CODE/port.json` нужно
разобрать: `null`/UNMAPPED не считается найденным адресом. В этой ревизии `A()`
возвращает исходный адрес, если PORT или запись в нём отсутствуют; только явный
`null` превращается в UNMAPPED и затем отклоняется `refuseUnmapped()`. `knob()`
допускает переданный `dflt`, тогда как `fact()` отказывает при отсутствии или
двойном определении. Поэтому отсутствие runtime-ошибки само по себе не
подтверждает правильность карты. Отдельно проверьте все используемые адреса и
параметры целевой сборки. Не превращайте неизвестные board facts в параметры
E143 «по умолчанию». Если надо менять
upstream без ясного разрешения на распространение, сохраните независимый
исследовательский отчёт/собственный адаптер и решите лицензирование отдельно.

### Шаг C. Добейтесь проверяемого stock UI без firmware-патча

Проверьте загрузку точных main/resources, kernel bring-up, меню, ввод, выход
назад, повторные нажатия, отмену и второе открытие. Подтвердите реальные размеры
панелей, формат ресурсных банков, palette/LUT, шрифты и strings. TFT и EVF
проверяйте отдельно, только если эта модель ими обладает.

Запишите все stand-ins и диагностику. Допустимое stock-отклонение должно быть
точно определённым и совпадать на всём маршруте. Не глушите класс ошибок, чтобы
получить красивый кадр. Сохраняйте GUI/control history, native RGB и PNG,
хэши реально загруженных модулей, executable и actions. На модели с иным
ресурсным форматом E-PL9 offsets, шесть видимых значков и 41-действий маршрут
не являются правильными эталонами.

### Шаг D. Перенесите updater отдельно от UI

Это отдельная исследовательская задача, не автоматический результат порта
OM-Emu. Найдите на целевой сборке валидацию, decode, выбор секций, copy/load,
program и readback. Для каждого boundary определите ABI, буферы, alias,
ownership, длины, контрольную сумму и обработку ошибок. Проверьте инструкции
против именно исполняемого образа. Не используйте адреса функций E-PL9.

Логическое file-backed хранилище и принцип read-only reopen переиспользуемы.
Но модель секций, оболочки, targets, erase/program, page/block, checksums и
порядок операций должны быть подтверждены для новой камеры. Выбранные у E-PL9
2048/131072 байта остаются **логическим допущением**, не универсальной NAND
геометрией. Штатный updater E-PL9 может вернуть 0 при ошибке нижней записи;
для новой сборки надо заново проверить её фактическое распространение ошибок.

Реальные инструкции исполняйте до известной границы, неизвестный call/MMIO
останавливайте. Если leaf заменён моделью, укажите это в отчёте. Ускоренный
цикл требует controls с исходным исполнением и сравнением всех регистров,
флагов, памяти и состояния цикла, а не только конечного checksum.

### Шаг E. Соедините стадии через неизменяемые квитанции

Ниже архитектурный контракт для нового порта, **не существующий универсальный
CLI или готовая JSON-схема**:

- идентификатор модели, точной сборки и поколения кандидата;
- исходный контейнер: размер/SHA-256 и полный список компонентов;
- runtime/reader/source/instruction-map identities, снятые до исполнения;
- для каждой операции: native callsite, диапазон, requested/programmed/readback
  хэши, результат, факт close/reopen и начальная версия хранилища;
- для каждого сохранённого компонента: полный размер, оболочка, target,
  полный хэш и отдельный payload-хэш;
- хэш фактического предшественника для виртуального возврата;
- explicit flags: virtual-only, physical-writes=false, reset-boot-proven=false,
  install-ready=false, плюс полный список моделей/непокрытых границ.

Потребитель должен сам перечитать файлы и проверить квитанции, а не доверять
одному `success`. Сначала захватите raw bytes, затем из **того же захвата**
делайте parse и hash record; повторно проверьте неизменность перед завершением.
Это касается source, JSON, overlays и кадров. Не записывайте cached RAM на диск
перед контрольным readback. Эти две ошибки уже были пойманы независимой
проверкой E-PL9 и исправлены до итоговой квалификации.

Стройте UI-вход только из проверенных сохранённых payload, затем проверьте
полное восстановление компонентов из overlays, включая хвосты, которые UI
не загружает. Для нового порта нужны собственные exhaustive patch spans и
эталоны. Нельзя подставлять старый кандидат, если новое хранилище повреждено.

## 6. Минимальная матрица приёмки нового порта

Не суммируйте всё в одно «работает». Для каждого пункта сохраняйте отдельный
passed/failed/not-run и причину:

1. **Source-only**: чистый checkout, synthetic unit tests, отсутствие firmware,
   media и чужого upstream в diff; отдельно перечислены skips из-за fixtures.
2. **CPU/платформа**: ISA controls, адресная карта, точная проверка исполняемых
   инструкций и полный список используемых аппаратных моделей.
3. **Stock UI**: bring-up, навигация, повторные/прерванные действия, все панели,
   стабильная диагностика и неизменяемые runtime/frame bindings.
4. **Updater**: валидный вход, повреждение каждой секции, check-only без записи,
   ошибки erase/program/readback, partial-write и post-checkpoint disk tamper.
   Возврат status 0 не заменяет сравнение всего содержимого.
5. **Связка**: stock -> candidate -> stock на действительных сохранённых
   файлах, свежие UI-сеансы и точные ограничения ожидаемых отличий.
6. **Физические этапы**: reset/BOOT, доставка update, flash controller/ECC,
   безопасный readback, восстановление, SD, sensor/ISP и реальные фотографии
   остаются not-run, пока не получены отдельные измерения на точном корпусе.

У текущего проекта исходные tests запускаются отдельно от приватных replay.
Если выполняли команды §4, сначала вернитесь **из `references/om-emu` в корень
E-PL9 Lab**. В примере именно из этого каталога работают `cd ../..` и пути
`scripts/`; из другого каталога выберите корень своего checkout явно. Нужен
Python 3.12+ и зависимости без RAW decoder:

```sh
cd ../..
python --version
python -m pip install -r requirements-emulator.txt
python -B -m unittest discover -s scripts -p 'test_epl9_virtual*.py' -v
python -B -m unittest discover -s scripts -p 'test_epl9_native_source_ui_qualification.py' -v
```

Для полного E-PL9 replay после восстановления **всех точных приватных входов**
следуйте двум предметным документам updater/UI выше. Используйте новый
игнорируемый output; предыдущие evidence и замороженный ART BIN не заменяйте.
Отсутствие приватных fixtures означает «не запускалось», а не разрешение
подставить похожую версию или ослабить guard.

## 7. Связь с будущими 31 рецептом, SD и Delete

Один UI/backend harness может обслуживать несколько поколений **после**
введения проверяемых модельных адаптеров. Он не делает firmware-реализацию
рецептов независимой от камеры. Нужны отдельные изменения:

- registry стабильных recipe IDs и UI mapping; число рецептов библиотеки не
  равно числу штатных ART-слотов;
- неизменяемый descriptor выбранного рецепта на processing job/кадр, отдельно
  для live view и JPEG, с WB/CFA/crop/cache/lifetime и callbacks;
- SD parser с bounds/checksums/version, независимыми defaults, session/media
  lifecycle, owned table buffers и отменой без use-after-free;
- Delete edge/press/release, debounce и режимный gate, чтобы не перехватить
  штатное удаление файлов или обработку чужого GUI;
- штатные и fault/regression маршруты с E-PL9-specific доказательствами,
  не только host-модель кнопки или файла.

Начинайте эти итерации в отдельной линии от двухрецептного кандидата. Успех
меню в OM-Emu не доказывает физический SD или применение таблиц TruePic.
Ни новый порт другой камеры, ни следующие E-PL9 функции не меняют готовый
ART-only кандидат до отдельного решения и проверки.
