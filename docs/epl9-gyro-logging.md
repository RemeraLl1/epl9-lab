# E-PL9: gyro logging alongside video

## Answer and scope

The owner explicitly wants gyro data saved during recording, including the
target [1920×1440 OpenGate/60](epl9-opengate-video.md). Firmware-side logging is
a plausible implementation route: the exact stock image contains stabilizer
diagnostic reads and CSV-writing code, and the follow-up below identifies the
underlying sample RAM and acquisition instructions in another component.
**A sufficiently fast, timestamped stream available during movies has not been
demonstrated.** This is not yet a working logger, and no diagnostic/vendor
command was sent to the camera.

The [eleventh timing pass](epl9-video-timing-sync.md#eleventh-november-4-pass-alternative-source-states-and-the-queued-pts-join)
closes the alternative source's queue-to-PTS-builder fragment. Its supply
ordinal and cyclic pixel-slot key still do not identify an exposure or buffer
write generation. A processing job preserves the capture key at +28, but its
completed-pixel/exposure association is open. The native TG `free` scheduler
accepts VD/phase-derived inputs without establishing a physical clock source.
Repeats and encoded-picture identity must be resolved before MOV CTTS can
provide useful exposure-aligned gyro timing.

The [tenth timing pass](epl9-video-timing-sync.md#tenth-november-4-pass-q-mode-gate-alternative-source-and-tg-free-callbacks)
narrows Q reachability: the known public configuration path produces 0/1,
while Q requires mode 2. An alternative source route carries a separate pixel
address plus software counters and supports cached/pool address reuse; it
does not yet carry a verified exposure/generation token to a MOV sample.
TG `free` comparison callbacks receive zero through the default dispatcher,
so their argument cannot serve as a sampled hardware time. Clock parent,
ordinary-60 frame identity, physical exposure phase and raw gyro timestamps
remain unresolved.

The [ninth timing pass](epl9-video-timing-sync.md#ninth-november-4-pass-q-constructor-and-the-real-request12-writer)
identifies Q's actual constructor and the request +12 sender. Q descriptor slots
and pixel-buffer indices are distinct from E's slot/generation; the Q constructor
does not copy E. A potential configuration/capture-key provenance remains
conditional on owner/snapshot/pixel lifetime. A logger must carry a matched frame
token across new/retained buffers and source/encoder/mux boundaries before CTTS
can map it to presentation time. Raw gyro acquisition timestamps remain open.

The [eighth timing pass](epl9-video-timing-sync.md#eighth-november-4-pass-q-completion-message-provenance)
traces completion command 36 through selected processing states to the source's
Q pointer. It does not yet attach `E+32` or an exposure ID to the completed
pixels or MOV sample. A retained-address sender can replace `Q+800`; logging
each notification as a new exposure would therefore be unjustified. Generation
and repeat provenance must be preserved before applying the MOV CTTS/edit map.

The [next timing/clock pass](epl9-video-timing-sync.md) identifies both components'
clock-reading instructions and a video PTS/delivery-clock association. It also
spells out the missing cross-clock and exposure/frame-identity links; delivery
time must not be used as exposure time.
The 2026-11-04 follow-up identifies a registered camera callback with separate
exposure/capture sequence fields. Its physical phase and movie-buffer/MOV join
remain unverified; the PTS input ordinal is generated by a software supply queue.
The second pass also traces a clock-reading marker to hardware TG IRQ bit 0,
and buffer arrays to PTS-bearing supply descriptors. The marker's physical
phase and the exposure-identity-to-MOV-sample mapping remain open.
The third pass closes the conditional marker-to-exposure-number join:
notification 147 copies the calculated TG-associated time into descriptor
`D+76`, alongside exposure sequence `D+44`. The time includes an offset and
software IRQ latency; physical phase, video-buffer identity, MOV sample PTS
and the stabilizer-to-main-clock mapping remain unverified. See the
[detailed chain](epl9-video-timing-sync.md#third-november-4-pass-camera-clocks-and-the-exposure-timestamp-join).
The fourth pass reaches a conditional image-work association and command 50,
named `NOTIFY_EXPOSE_CENTER`, with sequence at parameter `+0` and time at `+32`.
This provides an intended center-time path, not a physical timing calibration.
`D+76` also aliases body `+416`, which capture fallback can overwrite with a
fresh callback-time sample. Preserve provenance. **The fifth pass corrects the
earlier gate interpretation:** normalized values <=60 clear an accumulator and
return **1 (accept)**, so this gate does not exclude ordinary 60 fps. Runtime
per-frame delivery, raw gyro timestamps, cross-clock mapping and MOV association
remain unverified. The local original MOV uses 180000 video ticks/second,
3003 ticks/sample and composition reordering; supply order alone is insufficient
for synchronization. See the [fifth-pass evidence](epl9-video-timing-sync.md#fifth-november-4-pass-correcting-the-60-fps-gate-and-checking-an-original-mov).
The [sixth pass](epl9-video-timing-sync.md#sixth-november-4-pass-processing-records-pixel-source-descriptors-and-native-mov-timing)
extends capture identity to a processing record at offset +156, identifies
the source-address field +800 in video descriptors, and reaches native MOV
scale selection and CTTS run construction. Descriptor-instance/generation,
encoder-output identity and gyro/main-clock synchronization remain unresolved;
buffer reuse and repeated submission prevent treating an address as a frame ID.
The [seventh pass](epl9-video-timing-sync.md#seventh-november-4-pass-slot-generations-encoder-metadata-and-mov-sample-boundaries)
finds a per-slot build counter with explicit reset and local timestamp copies
through source and encoder packets to a mux read. The completed pixel-buffer
generation and actual connection instances remain unjoined. CTTS uses track
configuration and sample kind; the encoder tag alone is not an exposure-to-MOV
presentation-time mapping. The copied pool fields +800/+804 must not be assumed
pixel addresses: one producer supplies request kind/flags there.

This report uses only the E-PL9 1.1/build 1101 input identified in the
[video audit](epl9-opengate-video.md#exact-input-and-reproducible-evidence): stock
104552480 bytes, SHA-256
`aefab05396c43ecba0551b94a5d31f7e52350c18d6f4bf1d02d75761108e6028`;
decoded main 26214336 bytes, SHA-256
`8e39c335d54fd8ddea189db82fe708159f43f9995bba42c2cd47dd22b8814267`.
The owner's displayed version 1.1 does not identify installed bytes. All
main-component addresses below use analysis base `0x60400020`. Follow-up
addresses beginning `0x400…` belong to a separate decoded component with the
different base documented below; its small RAM addresses are in that component's
address space and are not main-CPU pointers.

## What the exact firmware establishes

The routine at `0x60f798d3..0x60f799fb` references:

- File offset `0xf01336`: `GYRO_DBG.csv`.
- File offset `0xf01343`: `cnt,Yaw,Pitch,Roll,X,Y,Z`.
- File offset `0xf0135e`: a seven-integer CSV row format.

Its caller at `0x60f5beb2` is decoded as a call to that routine. It uses
file helpers at `0x60fa4577` and `0x60fa4639`; the latter formats data and calls
the diagnostic file-write helper chain. This establishes a file-output code
path in the image, not successful SD output on this body.

The loop requests selectors **192, 193, 194** through `0x60fa6aab` and stores
the lower 16 bits of each returned first word in stack cells `+40/+42/+44`.
They are subsequently printed as Yaw/Pitch/Roll. The wrapper builds suboperation
10 through `0x60fa6916 → 0x60fa7870`. The latter supplies request `0x902b` to
`0x60fa71a8`. Exact name-table associations are:

| Association | Data location |
| --- | --- |
| `0x902b` → `MODEL_ORIENTED_DATA_IN` | Pair at `0x61278f38`; name at `0x61278ce5` |
| Suboperation `10` → `MDO_CONT_STAB` | Pair at `0x61279cf0`; name at `0x61279bd4` |

These names identify a model/stabilizer diagnostic layer. They do not establish
the gyro chip, bus, register map, interrupt, raw sample buffer or units.
The initial audit stopped at this layer. The follow-up below traces it further.
Treating its selectors as proven safe camera commands would still be unjustified.

The routine is unsuitable as a direct production logger:

- It also sets selector **150** to 1 before the loop and 0 afterwards through
  a different wrapper. State changes and interaction with normal recording are
  not characterized; do not invoke this calibration routine to test logging.
- It calls a wait-wrapper with argument 1000 before logging and argument 2
  inside each loop. The wait units and actual sample cadence are not verified;
  this does not prove 500 Hz acquisition.
- It writes a counter, **not a timestamp**, and performs sequential requests for
  the three axes. Their acquisition instants and coherence are unknown.
- A 12-byte local area is cleared before the loop. Visible stores fill only
  Yaw/Pitch/Roll; X/Y/Z at `+46/+48/+50` have no observed producer. External
  callees were not emulated. The CSV header does not establish accelerometer
  data; no usable X/Y/Z stream was found in this branch.
- Signed 16-bit formatting does not establish whether the inputs are angular
  rate, filtered values, angles, ADC counts or calibration results.

Other diagnostic text includes `GyroData_X[]/Y[]/Z[]`, drift statistics,
`rotMoveStep_X[]/Y[]/Z[]` and roll calibration. These are additional leads;
actuator steps must not be substituted for body angular velocity.

## Follow-up: producer and component boundary

The deeper audit adds this exact input from the **same stock E-PL9 package**:

| Item | Identification |

| Analysis base | **`0x40002800`**, distinct from container field `0x40002820` |

Startup at file offset 4 loads string pointers `0x400073ec/0x400073e2`;
under this base they resolve exactly to `task_drive_main\n` and `init_tsk\n`.
Other strings include `luke_main\cpu1\cmd\task_drive.c` and CPU0-labelled
paths. Call this the **CPU1-labelled component**; the strings alone do not prove
the physical processor assignment or that every branch is used by this body.
A search found 222 absolute string-start references at this base, versus 24
using the container field as base. The guarded audit checks the actual startup
instructions, strings, table contents and downstream consumers.

### Diagnostic request reaches a component register-read protocol

The static request path can now be followed substantially further:

| Stage | Native evidence |
| --- | --- |
| Main diagnostic envelope | `0x902b`, suboperation 10, through `0x60f59c31` and the diagnostic worker. Hash dispatch at `0x612776d0` resolves key `0x802a` to branch `0x60f5191d`. |
| Stabilizer request | `0x60f564b2` dispatches suboperation 10 to `0x60f5670a`; it sends packet type 3 / suboperation 10 through message 13 on queue 9. |
| Queue-9 receiver | Dispatch table `0x60584660` resolves message+1 key 14 to `0x604e8b3b`; through `0x604ea0d1 → 0x604d707d → 0x604d753d`, suboperation−1 key 9 reaches `0x604d7654`. |
| Selector read | `0x604d7654 → 0x604eae31 → 0x604eae4b`: operation **35**, one selector byte, result pointer, asynchronous driver action 162 with completion wait. |
| Driver descriptor | `0x604eb8b0` indexes 16-byte records at `0x60584824`; operation 35 selects `0x60584a54` = `(0x00020081, 0x604ec536, 0, 0x604ec56f)`. Command builder copies selector bytes; completion copies 16-bit results. |

This is a cross-component **static protocol match**, not a captured transaction
or an executed end-to-end test. It explains why slow diagnostic polling is a
poor production logger: it involves request queues, allocation, transport and
completion waits for values that already exist in the stabilizer component.

The bank-0 table starts at `0x4001b480`, with 12-byte records. Exact rows:

| Selector / diagnostic name | Table row | Component RAM | Descriptor / callback |
| --- | --- | --- | --- |
| 192 / Yaw | `0x4001bd80` | `0x493a` | `0x82c0` / 0 |
| 193 / Pitch | `0x4001bd8c` | `0x493c` | `0x82c1` / 0 |
| 194 / Roll | `0x4001bd98` | `0x493e` | `0x82c2` / 0 |

The width code consumed by the reader is two bytes. Yaw/Pitch/Roll are names
from the CSV caller, not a measured camera-axis convention. These small RAM
addresses must not be dereferenced from main firmware as if it shared this
address space.

### Where the values originate

Two distinct acquisition paths are visible:

- `0x4001a34e` reads a 16-bit value from **MMIO `0x9c060048`** into `d2`.
  At `0x4001a36d` it reads **`0x9c060044`**. For each channel it subtracts the
  oldest of three sample slots and adds the new value, storing rolling sums
  in **`0x493a/0x493c`**. The ring index at `0x4946` wraps at 3; sample slots
  start at `0x494e/0x4bf2`. These MMIO reads are the candidate capture points
  **before the software three-sample sum**. The ADC/MMIO peripheral's own
  filtering, conversion completion and electrical gyro source remain unknown.
- `0x4001a2b5` sends byte **`0xea`** through transfer helpers
  `0x4001621d/0x40016487`, receives two bytes in `0x61c2/0x61c3`, combines them
  high-byte first and stores the result into **`0x493e` at `0x4001a309`**.
  The associated initialization branch references `gyro rol read error!!`.
  This strongly identifies a roll-gyro read, but does not establish the chip,
  register datasheet, scale or whether the chip applies its own filtering.

The first routine is called at `0x400114c7`, in the incoming-data processing
path. The roll routine is called at `0x4001a0ad` by callback `0x4001a0aa`.
These are **different acquisition paths**, so reading the three RAM cells in
one operation does not establish a coherent simultaneous XYZ sample. Even the
two MMIO loads need conversion timing characterized. A raw logger should retain
per-channel acquisition timing/sequence until alignment is demonstrated.

Timer setup is also visible: initialization loads callback `0x4001a0aa` at
`0x4001a0fa`, installs it through `0x400172d6`, then starts it through
`0x4001731d`. Allocation requests timer ID 2 at `0x400172b4`. Setup passes
**12500** as a 16-bit comparator/configuration value; `0x40009884` writes it
through a timer register descriptor at `0x4000ecb8 + id×32`. ID 2's descriptor
points into `0x9c050040…`. **The timer input clock, divisor and exact period
are not established; 12500 is not a frequency or a timestamp.** The callback
also invokes `0x40013f23` on alternating counter parity. No hardware sample
rate is inferred from that counter.

### Timestamp finding and concrete logger boundary

No acquisition timestamp accompanies selectors 192–194, and no timestamp store
was found alongside the above sample publications. This is a scoped negative
result, not proof that the entire firmware lacks a usable clock.
`movp_get_time_conversion_spec` at `0x60ff8069` returns constants **600 and
90000**; its named dump at `0x6177da92` prints them as time-conversion values.
It must not be mistaken for a function returning the current acquisition time.
Neither that API nor an MOV presentation timestamp yet bridges the stabilizer
clock to exposure time.

The concrete implementation candidate is therefore:

1. Copy each new value at the **two MMIO reads and the roll transfer completion**,
   before later averaging/control processing. Attach a component-local hardware
   tick and per-channel sequence; keep original counts and flags. A tick taken
   after a transfer timestamps the read completion, not automatically the
   sensor's conversion instant; that latency needs characterization.
2. Use a bounded component-local ring and a **new batched telemetry path** to
   main firmware. Do not poll the three diagnostics at the desired sample rate
   or write to SD in the control callback. Available RAM, transport capacity,
   concurrent access and deadlines have not been measured; a new packet and
   opcode cannot be assigned safely until the protocol is fully mapped.
3. Establish a clock mapping between that tick counter and **actual movie
   frame/exposure events**. Characterize wrap, drift, variable read latency and
   channel phase. Preserve individual times when channels update separately;
   do not manufacture simultaneous XYZ vectors or a uniform timeline.
4. Drain batches from a main-CPU worker into a same-basename binary sidecar,
   with recording start/stop/split/error handling. Convert to GCSV after axis,
   units, clock and video alignment are known.

The sample sources are now specific enough to investigate such hooks offline.
However, **normal movie-time execution, operation with IS disabled, timer
frequency, video-clock synchronization and deployability remain unverified**.
The proposed logger may require changes to both components. No hook, packet
extension, firmware patch or camera write was applied.

## Proposed firmware implementation

The initial deliverable should be a separate log associated with each MOV,
followed by conversion on the workstation to Gyroflow `.gcsv`. It is not
necessary to alter the MOV muxer first. Direct GCSV generation in a background
task is another option once timing and filesystem cost are measured.

1. **Find the producer.** Trace normal stabilizer sampling, preferably an
   existing coherent XYZ sample publication point or controller mailbox/FIFO.
   Copy existing samples without changing the stabilizer's cadence or consuming
   a FIFO entry that its normal consumer needs. If only slow diagnostic reads
   are exposed, that path does not satisfy the logger requirement.
2. **Timestamp acquisition.** Use a monotonic timer tied to, or explicitly
   mapped onto, the video acquisition clock. Record the relation between first
   exposure and first sample, and frame/exposure timestamps where available.
   REC-button time and SD write-completion time are inadequate substitutes.
   Characterize clock wrap, drift and any batching delay from another controller.
3. **Buffer in RAM.** Publish fixed-size records with sequence numbers into a
   bounded ring buffer. A separate low-priority task writes blocks to SD.
   No filesystem call, allocation or text formatting belongs in the sample
   interrupt/stabilizer deadline. Count overruns and preserve timestamp gaps;
   never turn a dropped sample into an apparently valid uniform timeline.
4. **Follow actual recorder lifecycle.** Associate logs with the final movie
   basename and handle successful start, failed start, stop, card-full/error
   and split files. Drain/finalize outside the real-time path. Record gaps and
   discontinuities explicitly; do not delay or deadlock movie finalization.
5. **Calibrate and export.** Establish units, signs, orientation, scale, bias,
   saturation, filtering and temperature behavior from producer code and later
   measurements. Retain raw values and conversion metadata. Emit GCSV only
   when those mappings are known; do not invent an orientation or `gscale`.

Illustrative storage budget, **not a measured E-PL9 rate**: a 32-byte record
containing a timestamp, sequence, three signed values and flags at 1000 samples/s
is 32 kB/s, about 1.92 MB/min. Bandwidth is likely a smaller design issue than
access and timing, but free RAM, scheduling and SD latency remain unmeasured.
Capture each available real sample; a nominal 500–1000 Hz design aim is not
evidence that this sensor/controller can deliver it to main firmware.

Gyroflow's [GCSV specification](https://docs.gyroflow.xyz/app/technical-details/gcsv-format)
defines `t,gx,gy,gz`, time scaling to seconds and gyro scaling to rad/s. Optional
accelerometer data is not required for basic gyro stabilization. It recommends
timestamps based on the video clock. A same-basename sidecar is the intended
workflow; E-PL9 MOV association and actual importer behavior still need testing.
Keep a separate development manifest for frame markers, overrun statistics and
clock mappings rather than inserting unsupported columns into GCSV.

## Stabilization and validation

For initial post-stabilization experiments, use native **M-IS Off** and lens
stabilization off, while checking whether gyro sampling remains active. This
is a proposed later test configuration, not a configuration change performed
here. The [manual, p. 87](https://download.omsystem.com/pages/inst/epl9/manual_epl9_ENU.pdf)
distinguishes sensor-shift and electronic correction and describes an additional
crop with electronic correction. With moving sensor/lens or electronic warping,
body rotation alone does not fully describe motion in the saved image.
Combining those paths would need additional position/warp telemetry or separate
validation. If disabling IS also disables gyro publication, find a supported
sampling path that leaves the imaging geometry fixed.

First complete the producer/clock trace offline. Later authorized measurements
must establish stationary bias, controlled rotations for each axis, rate and
jitter, dropped samples, timestamp continuity, video alignment and readout time.
Gyroflow additionally needs a suitable lens/distortion model. Test long takes
and recorder error exits with logging enabled and disabled to detect regressions.

The shared audit script verifies the diagnostic strings, associations and native
instruction anchors; four synthetic tests validate its input/listing/output
guards. Neither test suite nor offline disassembly proves actual gyro logging.
Flashing and experimental vendor writes remain outside this phase.
